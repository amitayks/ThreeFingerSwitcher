## 9. Post-testing revisions (from user feedback on the first cut)

- [x] 9.1 **Lag fix — heavy work off the event-tap callback.** The delegate methods were running `openSwitcher` (snapshot + show + prefetch) and the cross-Space `raise` *synchronously inside* the keyboard `CGEventTap` callback, which the WindowServer blocks on — stalling the whole main-thread input pipeline (trackpad frames + highlight rendering) behind every keypress. Now each keyboard-delegate method dispatches its heavy work via `DispatchQueue.main.async` (FIFO order preserved); only cheap ownership bookkeeping stays synchronous. The pure state machine stays synchronous; the trackpad path is unaffected (it runs in the touch-frame handler, not a blocking tap). See design D9.
- [x] 9.2 **Backward is a symmetric step, not jump-to-first.** Shift+Tab now `selectLinear(delta: -1)` — the exact reverse of forward, crossing Spaces backward (first cut jumped to the origin, which never left the starting Space). Removed `origin` / `firstTarget` / `selectFirst`; the delegate's `first` intent became `step(forward:)`. Spec requirement and `KeyboardSwitcherTests` / `SwitcherModelTests` updated.
- [x] 9.3 `swift build` + `swift test` green after both revisions (1464 tests, 0 failures).
- [x] 9.4 **Cross-Space commit focus — first attempt (insufficient; LATER REVERTED by §9.7).** Suspected the async commit (§9.1) delayed the SkyLight `setFront` handshake, so reverted `keyboardSwitcherCommit` to raise **synchronously**. This did NOT fix the deselect — the real cause was elsewhere (§9.5) — and, once §9.5 landed, the synchronous commit was left both vestigial AND the cause of the "stuck overlay on a fast ⌘-Tab" bug, so §9.7 reverted it back to deferred.
- [x] 9.6 **First Tab advances immediately (native-⌘-Tab feel).** The opening Tab now opens the overlay AND steps once in its direction (⌘-Tab → next window, ⌘-Shift-Tab → previous), so a quick press-release lands on the adjacent window instead of resting on the current one. One-line change in `KeyboardSwitcher.tab` (emit `open` then `step(forward: !shift)` on the armed→active transition); spec / design / `KeyboardSwitcherTests` updated. `swift test` green (1464, 0 failures).
- [x] 9.5 **Cross-Space "selected then deselected" — ACTUAL root cause (two-agent investigation).** PRE-EXISTING bug in the shared `WindowService.raise()`, not the keyboard driver — ⌘-Tab just exposed it (it crosses Spaces on every commit; trackpad off-Space commits needed a rare vertical edge-scrub). The polling **hold-guard** (`offSpaceHoldTick`) that re-fronts the target to defeat the destination Space's ~300–500ms focus-restore was scheduled only `if !window.isOnCurrentSpace && StageManager.isEnabled`; with Stage Manager OFF, an off-Space raise had NO re-front, and the single +180ms watchdog is single-shot-on-pass (probes before the steal → retires). **Fix (`WindowService.swift`):** run the hold-guard for EVERY off-Space raise (drop the `&& StageManager.isEnabled` gate); keep the full ~2.4s window under Stage Manager (repeated re-steals), use a shorter ~1.2s window (`offSpaceHoldShortTicks`) for a plain switch (one-time steal) so it doesn't fight a deliberate user switch-away for as long. Heals the trackpad off-Space commit and the Dock-preview commit too (all funnel through `raise()`). `swift build` + `swift test` green (1464, 0 failures).
- [x] 9.8 **Arrow-key navigation while ⌘-Tab is open (Windows-Alt-Tab parity).** While the switcher is open and ⌘ is held: Left/Right step through windows (identical to Shift+Tab / Tab — linear, flowing across Spaces, `→ → → next Space →`) and Up/Down jump directly between Spaces. New `SwitcherArrow` enum + `arrow(_:)` on the pure `KeyboardSwitcher` (guarded to `.active` — arrows never OPEN the switcher); `KeyboardSwitcherTap` maps arrow keycodes (123–126) and consumes them ONLY while a session is active (⌘-arrow shortcuts untouched when closed); `AppCoordinator.keyboardSwitcherStepSpace(up:)` (deferred) jumps via the trackpad's `switchSpace` with the same `emitRowStep` direction convention (`up ? +1 : -1`, flipped by `reverseVerticalDirection`) so Up arrow == up-scrub. Spec (new "Arrow keys navigate…" requirement) / design (D10) / `KeyboardSwitcherTests` (3 new tests) updated. `swift build` + `swift test` green (1467, 0 failures).
- [x] 9.7 **Stuck overlay on a fast ⌘-Tab press-release — revert the synchronous commit (§9.4 undone).** A really fast ⌘-Tab left the overlay STUCK on screen (highlight moved, but it never committed/dismissed — cleared only by the next, slower ⌘-Tab). Root cause: the synchronous `keyboardSwitcherCommit` (§9.4) ran OUT of FIFO order relative to the deferred open/step (§9.1). The `.cgSessionEventTap` callback processes the whole ⌘-down / Tab / ⌘-up burst before the run loop drains the deferred `open`/`step`, so the synchronous commit ran FIRST — it saw `overlay.isVisible == false` (open hadn't run), dismissed nothing, and the `open`/`step` then drained and showed/advanced an overlay with no commit left to dismiss it (aggravated under rapid repeats where the next cycle re-claims `switcherOwner == .keyboard`, letting a stale open show the overlay). **Fix (`AppCoordinator.swift` `keyboardSwitcherCommit`):** defer through `DispatchQueue.main.async` like open/step/cancel (guarding `switcherOwner == .keyboard`), restoring FIFO so open → step → commit always drain in press order and commit always dismisses the overlay it followed. Safe now because §9.5 made the raise's hold-guard cover EVERY off-Space raise — focus-sticking no longer needs a synchronous raise (§9.4's premise), so the sync commit was vestigial AND the cause of the stuck bug. Keeps §9.6 (first Tab opens + steps). The pure `KeyboardSwitcher` state machine is unchanged (commit is still emitted synchronously from `commandUp`; only the coordinator's HANDLING defers), so `KeyboardSwitcherTests` is unaffected. Design D9 + the "Browsing never stalls…" spec requirement/scenario corrected (commit defers again; focus guaranteed by the hold-guard, not a synchronous raise). `swift build` + `swift test` green (1464, 0 failures).
